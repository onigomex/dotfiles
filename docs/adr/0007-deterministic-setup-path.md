# 0007: セットアップの実行経路には出力が決定的なものだけを置き、AI にやらせたい作業はリポジトリ内のスキルに置く

## Context and Problem Statement

`make list` に並ぶ一行説明や各ロールの `README.md` の質を上げたい。39 ロールぶんあり、人手で書くのは大変なので AI に任せたい。素直に考えると `claude -p` を `make` から呼ぶ案が浮かぶ。

このリポジトリは、`curl` でリポジトリを取得 → `install.sh` が動く → それが `make install` を叩く、という 1 本道で**まっさらな mac を再現可能に立ち上げる**ためのものである。`claude` はこのリポジトリが入れる対象の 1 つ（`roles/claude`）にあたる。

**ただし「このリポジトリが入れたツールを、後続のロールが使う」こと自体は既に認めている。** 例として `roles/zsh/install.sh` は `ghq`（`roles/ghq` が入れる）を使っており、`roles.list` の並び（`ghq` が 7 行目、`zsh` が 8 行目）で順序を保証している。便利なツールがあるのに自前で実装し直すのは負担が大きいためである。

**したがって問題は導入順ではない。** 決める必要が出たのは、AI が他のツールと性質が違うからである。

| | 性質 |
| --- | --- |
| `ghq` など従来のツール | **ある入力に対して、いつも同じ出力を返す**（決定的） |
| AI（`claude -p`） | **同じ入力でも出力がブレる** |

これまで AI はこのツールの構成要素として登場していなかった。ここで初めて「AI をどこに置くか」を決める必要が出た。

決める範囲は「セットアップの実行経路に何を置いてよいか」「AI にやらせたい作業をどこに置くか」「判定を散文とコマンドのどちらに寄せるか」の 3 点。

## Considered Options

* 実行経路には出力が決定的なものだけを置き、AI 用の手順はこのリポジトリの `.claude/skills/` に置く
* `make` から `claude -p` を呼ぶ
* スキルを個人のグローバル領域（onigomex/claude）に置く

## Decision Outcome

Chosen option:「実行経路には出力が決定的なものだけを置き、AI 用の手順はこのリポジトリの `.claude/skills/` に置く」。理由は 3 つ。

- **出力が決定的なものだけに限る理由**: 出力がブレると install の結果が再現しなくなる。このリポジトリの目的は「まっさらな mac を再現可能に立ち上げること」なので、実行経路に出力のブレるものを入れると目的そのものを壊す。**逆に言えば、ある入力に対していつも同じ出力を返すものなら認められる**——`ghq` を後続のロールが使うのが問題にならないのはそのためである。**判定軸は「このリポジトリが入れたツールかどうか」ではなく「出力が決定的かどうか」。** 現時点で出力がブレるものは実質 AI だけだが、**規則は AI ではなく出力の性質にかけている。**
- **スキルをこのリポジトリに置く理由**: スキルなら AI があるときだけ使える追加物になり、無くてもツールは完全に動く。人が読んでも同じ手順を踏めるので、**AI 用の指示書がそのまま人間用の手順書になる**。
- **判定をコマンドに寄せる理由**: 散文で「確認すること」と書いても、実行するのは毎回違うセッションで判定が揺れる。コマンドにすれば答えが 1 つに決まり、スキルは「`make doctor` を通す」と書くだけで済む。人が同じコマンドで確認できるのも同じ利点。

具体的にはこう決める。

1. セットアップの実行経路（`Makefile` / `scripts/` / `roles/*/install.sh`）には、**ある入力に対していつも同じ出力を返すものだけ**を置く。出力がブレるものを install の途中に入れない。現状それに当たるのは AI（`claude -p` 等）である。
   - **セットアップ中に入れたツールを後続のロールが使うのは、出力が決定的である限り認める。** 順序は `roles.list` の並びで保証する（例: `ghq` → `zsh`）。
2. AI にやらせたい作業は `<repo>/.claude/skills/<name>/SKILL.md` に手順として置く。ツールは雛形と `FIXME` を置くところまで、その `FIXME` を埋めるのがスキルの担当、という切り分けにする。
3. 機械で判定できるものは `make doctor` のようなターゲットにし、スキルからはそれを呼ばせる。

却下した案は 2 つ。「**`make` から `claude -p` を呼ぶ**」は install の結果が再現しなくなる。加えて `claude` はこのリポジトリが入れる対象なので、導入順を意識しないと使えないツールになる。「**スキルを個人のグローバル領域（onigomex/claude）に置く**」は、このリポジトリの構造（`roles/` / `roles.list` / `make`）に固有の手順なので、無関係なリポジトリで発火してほしくない——リポジトリと一緒に travel するほうが実態に合う。

### Consequences

* Good, because install の結果が再現する。まっさらな mac から流しても、何度流し直しても同じ状態になる。
* Good, because `make` だけで使う場合の体験は今までどおり。AI はあれば質が上がる、無くても困らない、という位置づけになる。
* Good, because 規則を出力の性質にかけたので、AI 以外に出力のブレるものが出てきても、そのまま判定できる。
* Bad, because ロール間の順序依存を支えているのは `roles.list` の並びだけで、依存そのものはどこにも宣言されていない。増えると、どのロールがどのロールに依存しているのかが追いにくくなる。
* Bad, because 機械判定に寄せるぶん `make` のターゲットは増えうる。増やすときは「覚えるコマンドを増やさない」方針（[ADR 0005](0005-install-only-no-update-hook.md)）と衝突しないか毎回見る。
* Neutral, because スキルが増えると `.claude/skills/` がこのリポジトリの一部として育つ。個人の Claude 設定（onigomex/claude）とは役割が別なので、混ぜない。

## More Information

### Review Trigger (local)

- **AI の出力が、同じ入力に対して決定的になったとき。** 判定軸が「出力が決定的かどうか」である以上、そこが変われば結論も変わる。
- **`curl` → `install.sh` → `make install` でまっさらな mac を立ち上げる、という使い方をやめたとき。** 再現性を要求する理由が消えるので、決定 1 の前提ごと無くなる。
- ロール間の順序依存が増えて、`roles.list` の並びを追うのが負担になってきたとき（決定 1 の例外をどこまで認めるかを見直す）
- `make` のターゲットを増やす提案が出て、「覚えるコマンドを増やさない」方針（[ADR 0005](0005-install-only-no-update-hook.md)）と実際に衝突したとき（決定 3 を見直す）

- [ADR 0006](superseded/0006-tool-works-without-ai.md): 本 ADR が置き換えた文書。制約を「mac の初期状態から流す前提」＝導入順の問題として書いていたが、実際には導入順は問題ではなく、出力が決定的かどうかが判定軸だった。
- [ADR 0005](0005-install-only-no-update-hook.md): 覚えるコマンドを増やさないために update を廃止した決定。ターゲットを増やすときはこれと突き合わせる。
