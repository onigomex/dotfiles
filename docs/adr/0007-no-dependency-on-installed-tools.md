# 0007: セットアップが依存してよいのは mac の初期状態と homebrew だけにし、AI 等の作業はリポジトリ内のスキルに置く

## Context and Problem Statement

このリポジトリは「新品の mac を、手でポチポチ設定せずに、再現可能な形でワンコマンドで立ち上げる」ために作った。想定している使い方は 1 本道である。

1. リポジトリを `curl` で取得する
2. `install.sh` が動く
3. それが `make install` を叩く
4. 基本セットアップが整う

**この経路が走る時点では、まだ何も入っていない。** 入れるのはこのリポジトリ自身である。

きっかけは AI だった。`make list` に並ぶ一行説明や各ロールの `README.md`（39 ロールぶん）の質を上げたく、「`claude -p` を `make` から呼べば楽になる」と考え始めたところでこの問題にぶつかった。`claude` はこのリポジトリが入れる対象の 1 つ（`roles/claude`）なので、セットアップがそれに依存すると、**セットアップを始めるためにセットアップが終わっている必要がある**。

ただし**問題は AI 固有ではない**。`jq` でも `fzf` でも `ghq` でも同じで、このリポジトリが入れたツールをセットアップの手順に載せ始めると、何が何に依存しているのかが追えなくなり、セットアップ自体が複雑になる。

例外は **homebrew** だけである。それが無いと `brew install <ツール>` が成立せず、そもそも起点が作れない。

なお**セットアップが終わったあと、そこで入れたツールを前提に作業するのは何の問題もない**。制約がかかるのはセットアップの実行経路だけで、日々の作業には及ばない。

決める範囲は「セットアップの実行経路が何に依存してよいか」と「AI にやらせたい作業をどこに置くか」の 2 点。

## Considered Options

* 依存先を mac の初期状態と homebrew だけに限り、AI 用の手順はこのリポジトリの `.claude/skills/` に置く
* AI（`claude`）だけを禁じ、他の自前導入ツールへの依存は許す（＝ ADR 0006 の範囲）
* `make` から `claude -p` を呼ぶ
* スキルを個人のグローバル領域（onigomex/claude）に置く

## Decision Outcome

Chosen option:「依存先を mac の初期状態と homebrew だけに限り、AI 用の手順はこのリポジトリの `.claude/skills/` に置く」。理由は 4 つ。

- **依存先を絞る理由**: このリポジトリはセットアップをする側なので、自分が入れたものに依存すると循環する。加えて依存を積み上げると、何が何に依存しているかが追えなくなり、セットアップが複雑になる。
- **homebrew だけ例外にする理由**: それが無いと `brew install` が成立せず、セットアップの起点が作れない。例外はここだけで足りる。
- **AI を特別扱いしない理由**: AI は「このリポジトリが入れたツール」の一例にすぎない。AI だけを禁じる書き方では、`jq` や `ghq` に依存し始めたときに歯止めが無い。実際 ADR 0006 の範囲では、後述の `roles/zsh` → `ghq` 依存を違反として捉えられなかった。
- **スキルをこのリポジトリに置く理由**: スキルなら AI があるときだけ使える追加物になり、無くてもツールは完全に動く。人が読んでも同じ手順を踏めるので、**AI 用の指示書がそのまま人間用の手順書になる**。このリポジトリの構造（`roles/` / `roles.list` / `make`）に固有の手順なので、リポジトリと一緒に travel するほうが実態に合う。

具体的にはこう決める。

1. セットアップの実行経路（`Makefile` / `scripts/` / `roles/*/install.sh`）が依存してよいのは、**mac の初期状態にあるもの**と **homebrew** だけ。このリポジトリが入れるツールを呼ばない。`claude` はその一例にすぎない。
   - **例外**: ロールが自分で入れたツールを、同じ `install.sh` の中で使うのはよい（例: `roles/python` は `brew install uv` の直後に `uv python install --default` を実行する）。依存が 1 ロールの中に閉じており、外から順序を気にする必要が無いため。
2. AI にやらせたい作業は `<repo>/.claude/skills/<name>/SKILL.md` に手順として置く。ツールは雛形と `FIXME` を置くところまで、その `FIXME` を埋めるのがスキルの担当、という切り分けにする。
3. 機械で判定できるものは `make doctor` のようなターゲットにし、スキルからはそれを呼ばせる。散文で「確認すること」と書いても実行するセッションごとに判定が揺れるが、コマンドにすれば答えが 1 つに決まり、人が同じコマンドで確認できる。

却下した案は 3 つ。「**AI だけを禁じる**」（ADR 0006 の範囲）は、同じ問題が他のツールで起きたときに歯止めが無い。「**`make` から `claude -p` を呼ぶ**」は循環依存に加え、AI を挟むと同じ入力でも出力が揺れて install の結果が再現しなくなる。「**スキルを個人のグローバル領域に置く**」は、このリポジトリ固有の手順が無関係なリポジトリで発火してしまう。

### Consequences

* Good, because まっさらな mac で `curl` → `install.sh` → `make install` の 1 本道が、導入順を意識せずに通る。
* Good, because `make` だけで使う場合の体験は変わらない。AI はあれば質が上がる、無くても困らない、という位置づけになる。
* Bad, because **この決定に照らすと、既に違反が 1 件ある。** `roles/zsh/install.sh` は `ghq`（`roles/ghq` が入れる）を使っており、`roles.list` の並び（`ghq` が 7 行目、`zsh` が 8 行目）によって暗黙に成立している。`make install ROLE=zsh` を単体で流すと `ghq get` の行で落ちる（`ghq` 不在の PATH で再現して exit 127 を確認）。この決定に合わせるなら直す必要がある。
* Bad, because 機械判定に寄せるぶん `make` のターゲットは増えうる。増やすときは「覚えるコマンドを増やさない」方針（[ADR 0005](0005-install-only-no-update-hook.md)）と衝突しないか毎回見る。
* Neutral, because スキルが増えると `.claude/skills/` がこのリポジトリの一部として育つ。個人の Claude 設定（onigomex/claude）とは役割が別なので、混ぜない。

### Confirmation

**現時点では自動判定は無い。** ロールの `install.sh` が他ロールの入れたツールを呼んでいないかの検査は、決定 3 の形で `make doctor` に足せる。上記の `roles/zsh` → `ghq` の件を直すときに、あわせて入れるのが自然。

## More Information

### Review Trigger (local)

- **`curl` → `install.sh` → `make install` でまっさらな mac を立ち上げる、という使い方をやめたとき。** この制約はその 1 本道を守るためだけにあるので、前提が消えれば決定ごと不要になる。**入れる対象が変わっただけ（例: `claude` が mac に最初から入るようになった）では発火しない**——制約は特定のツールではなく「自分が入れたものに依存しない」という形にかかっている。
- homebrew 以外に「これが無いと起点が作れない」ものが出てきたとき（例外が 1 つで足りなくなる）
- 依存を許さないために `roles/*/install.sh` が不自然に複雑になり始めたとき（複雑さを避けるための決定が、複雑さを生んでいることになる）

- [ADR 0006](superseded/0006-tool-works-without-ai.md): 本 ADR が置き換えた、同じことを AI に限定して決めていた文書。
- [ADR 0005](0005-install-only-no-update-hook.md): 覚えるコマンドを増やさないために update を廃止した決定。ターゲットを増やすときはこれと突き合わせる。
