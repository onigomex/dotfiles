# docs

**読むもの・記録**の置き場。実行するもの（`Makefile` / `scripts/` / `roles/`）はリポジトリ直下に置く。

| 置き場 | 何を置くか |
| --- | --- |
| [adr/](adr/) | 意思決定の記録。現行の決定は直下、効力を失ったものは `adr/superseded/`。書き方は `adr` スキルが正 |
| `role-<ロール名>-spec.md` | そのロールの仕様。下の規則に従う |

## `role-<ロール名>-spec.md` の規則

- **1 ロール 1 ファイル。** そのロールが提供する仕組みごとに、**見出し 2 を足す**（ファイルを増やさない）。
- 例: [role-zsh-spec.md](role-zsh-spec.md) は `# role zsh spec` の下に `## .zsh.d の仕様` を持つ。zsh role が別の仕組みを提供するようになったら、`##` を並べる。
- **なぜ仕組み単位でファイルを分けないか**: ファイル名が仕組み名に依存すると（`zsh-d-spec.md` など）、**その仕組みを忘れた時点でファイル名も意味を失う**。ロール名なら残る。
- **なぜ `roles/<ロール名>/` に置かないか**: 仕様は「読むもの」で、`roles/` は「動くもの」。加えて `.zsh.d` のように**他のロールから使われるインターフェース**は、そのロールの中に隠れているより `docs/` にあるほうが見つかる。

**この規則はまだ ADR にしていない。** 実例が `role-zsh-spec.md` の 1 個しかなく、1 例から一般則を書くと外しやすいため（実際 ADR 0006 → 0007 でそれをやった）。**2 個目の `role-*-spec.md` が出たら ADR 化を検討する。**
